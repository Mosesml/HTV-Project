# K9: Duress-identical cancel (overnight run)

Branch `kean/k9-duress-cancel`, cut from `kean/k8-active-session` at `06c266f`. Built unattended: every question was answered with the recommended option, and each answer is listed under "Decisions taken on Kean's behalf".

## Plan

### Requirements, restated

- K9 (PRD D7, UI-4): after a correct PIN, the PIN entry screen runs **one code path** for the safe and the duress PIN: a fixed 600 ms "Cancelling…", the same haptic (`expo-haptics`), then the same "Cancelled. Stay safe." screen. Depends on K6.
- `pinResult(kind)` is called **without awaiting it** (fire and forget). Neither its speed nor its failure may change anything on screen.
- A wrong PIN shows a neutral retry. The 3-strike rule stays in Swift (ESC-7): the screen reports every `wrong` and does not count.
- The duress rule (WORK_ORDER.md): nothing on screen may differ between the two PINs. After a duress PIN, Swift keeps emitting `monitoring` and never sends an `onEscalation` the Alert screen would show.
- A test renders the safe and the duress path and asserts identical rendered output **and timing**.
- Done when: side-by-side recordings of both PINs match frame for frame.

### Grounding in the existing code

- `app/src/screens/PinEntryScreen.tsx` (K6): `showCancelled(kind)` is already the shared path (sets `status = 'cancelled'`, sends `pinResult` with `.catch`). K6.md says K9 adds the 600 ms and the haptic inside it, keeping the Keychain-failure path ("Couldn't check your PIN") outside.
- `app/src/pin/securePinStore.ts`: `verify` hashes under both salts for every entry, so the time to reach "Cancelling…" is the same work for both PINs.
- `app/src/navigation/phaseNavigation.ts`: `monitoring` never moves the wearer off `/pin`, so the cancel screens stay up for both PINs until Done.
- `app/__tests__/screens/PinEntryScreen.test.tsx`: the K6 duress test compares the final trees; K9 extends this to every frame.
- `app/__tests__/screens/CheckInScreen.test.tsx` (K7): the whole-file fake-clock pattern (`doNotFake: ['nextTick', 'queueMicrotask']`, `runOnlyPendingTimers` in `afterEach`), reused here.
- `app/jest.setup.ts` and `app/test-utils/fakeSecureStore*.ts`: the pattern for a native-package stand-in with a controls accessor; copied for `expo-haptics`.
- `app/src/ui/theme.ts`, `ActionButton.tsx`: shared type and button styles for both cancel steps.

### Risks

- **Something on screen differs by PIN.** Mitigation: the kind is passed straight to `sendPinResult` and never stored in state, so the render cannot depend on it; the frame test compares every frame.
- **`pinResult` latency or failure leaks onto the screen.** Mitigation: it is not awaited and its rejection is swallowed; tests run the sequence with a `pinResult` that never resolves and one that rejects.
- **Haptics unavailable** (Low Power Mode, a Simulator, an old phone) rejecting. Mitigation: fire and forget with the error swallowed; a test checks a failing haptic changes nothing.
- **Timer leaks / state updates after unmount.** Mitigation: the timer is cleared on unmount; tested.
- **A double submit starting two sequences.** Mitigation: K6's in-flight guard plus a started-once guard in the hook.
- **New native package.** `expo-haptics` needs a rebuild on every phone. Mitigation: prebuild, `pod install` and the simulator build are run here; the test guide says to rebuild.
- **Jest can't prove real frames match.** A Jest "frame" is the rendered tree at 16 ms steps; real recordings also include the keyboard animation and the haptic itself. The guide covers the side-by-side recording on the phone.

## Decisions taken on Kean's behalf

1. **The 600 ms starts when the PIN is accepted**, not at the tap on Submit. Before that the screen shows the same "checking" frame for every entry (Submit disabled), and K6's `verify` does the same hashing for every entry, so both PINs reach "Cancelling…" after the same work. Starting at the tap would have meant showing "Cancelling…" before knowing the PIN was wrong.
2. **`pinResult` is sent first, then the haptic, then the screen changes**, all in the same tick. Swift gets the duress signal as early as possible; nothing waits on either call.
3. **Haptic: `notificationAsync(Success)`**, once, as "Cancelling…" appears. It is the standard "this worked" tap and is the same for both PINs.
4. **No haptic on a wrong PIN.** The guidance asks for a neutral retry; the text "Wrong PIN. Try again." is the retry. (A different haptic for wrong would not break the duress rule, but was left out to keep the PIN screen quiet.)
5. **"Cancelling…" has nothing to tap.** No Done or Back button during the 600 ms, so the sequence always plays in full and looks the same every time.
6. **No spinner or animation** on "Cancelling…": text only. An animation adds frames that could drift between two recordings; plain text is identical by construction.
7. **A second correct PIN during the sequence is ignored** and does not restart the 600 ms (backs up K6's in-flight guard).
8. **Haptic failures are swallowed** like `pinResult` failures: a Simulator, Low Power Mode or an old phone has no haptics, and that must not change what shows.
9. **The PIN screen tests moved to the fake clock** (K7's pattern) rather than waiting 600 ms of real time per test.
10. **No VoiceOver announcement was added.** The headings change on screen; an `announceForAccessibility` call would be the same for both PINs, but it is left for the accessibility pass (D12 / BL8).
