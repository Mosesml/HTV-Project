# K6: PIN gate with salted hashes in expo-secure-store (overnight run)

Branch `kean/k6-pin-gate`, cut from `kean/k5-setup` at `a1c1819`. Built unattended: every question was answered with the recommended option, and each answer is listed under "Decisions taken on Kean's behalf".

## Plan

### Requirements, restated

- K6 (PRD D6, PRV-4, ESC-7): a PIN gate. Both PINs are stored as salted hashes in `expo-secure-store` (the iOS Keychain), never in plain text. `verify(pin)` returns `safe`, `duress` or `wrong`, and the PIN entry screen sends that result to Swift with `pinResult`. Depends on K4.
- Three wrong PINs fire the escalation (ESC-7). Per the seam table, counting wrong attempts is Swift's job (`pinResult('wrong')` three times); the React Native side reports every wrong entry and does not count.
- Hook K5's PIN step to the real store: `appPinStore()` in `app/src/pin/PinStoreProvider.tsx` returns the secure store, and the PIN entry screen calls `verify()` in place of the 1111 / 9999 placeholder.
- The duress rule (WORK_ORDER.md) must keep holding: safe and duress share one code path to "Cancelled. Stay safe.", and `pinResult` is sent without waiting for it.
- Done when: unit tests for all three results. Plus tests that the stored values are not the plain PINs.

### Risks

- **A safe and a duress PIN become distinguishable by timing or by screen.** Mitigation: `verify` always reads the record once and hashes the entry with both salts before comparing, so both PINs (and wrong ones) do the same work; both results still go through `showCancelled`; the identical-tree test stays.
- **Locking the wearer out.** If the Keychain read fails, treating the entry as wrong would count a strike toward escalation for a correct PIN. Mitigation: a failed check shows "Couldn't check your PIN. Try again." and sends no `pinResult`; the check-in timeout still escalates if the wearer never gets through.
- **Plain PINs leaking.** Mitigation: only salts and hashes are written; `PinValidationError` never includes the PINs; a test searches the stored value for the PINs.
- **Keychain items outlive an uninstall on iOS.** After a reinstall the settings file is gone but the PINs are still set. Mitigation: Setup already says "Leave both PINs blank to keep the ones you set." and Debug → Reset settings clears both; documented below.
- **Native package needs a rebuild.** `expo-secure-store` has native code, so existing dev builds must be rebuilt. Mitigation: prebuild, `pod install` and the simulator build are run here; the test guide says to rebuild.
- **4 to 8 digit PINs are a small space**, so a stolen salt and hash could be brute-forced whatever the hash cost. Mitigation: the Keychain (`AFTER_FIRST_UNLOCK_THIS_DEVICE_ONLY`, never migrated to another device or backup) is the real protection; the record carries a version so a stronger scheme can replace it later.

## Decisions taken on Kean's behalf

1. **One Keychain item for both PINs**, as versioned JSON. A save replaces both at once or leaves both as they were, so the store can never hold a new safe PIN with an old duress PIN.
2. **Salted SHA-256, one pass, a 16-byte salt per PIN, new salts on every save.** Key stretching (PBKDF2 and the like) doesn't help much with 4 to 8 digit PINs: even 10^8 guesses is cheap for anyone who has the salt and hash. The real protection is the Keychain. The record has `version` and `algorithm` fields, so a stronger scheme can replace it later, and a record it doesn't recognise reads as "no PINs".
3. **`AFTER_FIRST_UNLOCK_THIS_DEVICE_ONLY`, keychain service `raveguard`.** The item can be read whenever the app runs after the first unlock since boot, so a background launch still knows whether PINs are set. It is never copied to iCloud backups or a new phone. `requireAuthentication` (Face ID) is off: a check-in can't wait on Face ID, and under duress it would get in the way.
4. **`verify` always hashes the entry under both salts before comparing**, and the compare runs over the whole string. Safe, duress and wrong entries all do the same work, which backs up the duress rule. (On screen they were already identical.)
5. **A Keychain error is not a strike.** If the PINs can't be read, the screen says "Couldn't check your PIN. Try again." and sends no `pinResult`. Treating it as `wrong` would let a Keychain glitch escalate a wearer who typed the right PIN. If it never recovers, the check-in timeout still escalates. The message is the same whichever PIN was typed.
6. **The wrong-attempt count stays in Swift.** The seam table gives the 3-strike rule to `pinResult`, and Justin's `SessionManager` already counts. The screen sends every wrong entry and does not count on its own. PRD D6's "counts wrong attempts" is met by the Swift side (J8 tests it).
7. **No PINs set means every PIN is wrong, with a plain note on the PIN screen.** There is no fallback to 1111 / 9999: a fallback anyone could guess would cancel any check-in. Setup won't save without PINs, so this only happens after Debug → Reset settings, or with a session started from Debug.
8. **A damaged record reads as "no PINs"** (Setup then asks for them again) instead of an error. On the PIN screen that means every PIN is wrong, which fails toward escalation rather than toward a silent cancel.
9. **The Face ID usage text is left out** (`faceIDPermission: false` in the plugin), since nothing asks for Face ID.
10. **Keychain items outlive an uninstall on iOS, and that was left alone.** After a reinstall the settings are gone but the old PINs still work; Setup says "Leave both PINs blank to keep the ones you set." and Debug → Reset settings clears them. Wiping the Keychain on first launch would need a marker file, which isn't needed for the demo.
11. **The in-memory `createMemoryPinStore` stays**, for tests that need a `PinStore` without the Keychain. Its own tests are unchanged.
12. **No `@types/node`.** Tests load Node's `crypto` through `jest.requireActual` with a small local type (`test-utils/nodeCrypto.ts`), as K4's `randomUUID` mock already did, so no new dev dependency is needed.
