# K5: setup flow with both PINs (overnight run)

Branch `kean/k5-setup`, cut from `kean/k4-settings` at `0c823a2`. Built unattended: every question was answered with the recommended option, and each answer is listed under "Decisions taken on Kean's behalf".

## Plan

### Requirements, restated

- K5 (PRD D5, UI-1, PRV-3): a setup flow where the wearer enters two ordered contacts and venue staff, a permissions grid per recipient (`receiveAlerts`, `seeLocation`, `seeFullBrief`, `canResolve`), the check-in interval (30 or 60 min), the loudness target, a self-description, and both PINs (safe and duress), which must differ. Depends on K4.
- Persist the settings through K4 (`useSettings().save(next)`, which validates, writes the file and calls `configure()`).
- PIN storage is K6, which doesn't exist yet. The PIN step hands both PINs to a small `PinStore` interface that K6 will implement with `expo-secure-store`; an in-memory stub implements it for now.
- Component tests for the flow and for the "PINs must differ" rule.
- Done when: scenario 7's setup (Contact 1 sees location, Contact 2 doesn't, venue staff present) is done in under 60 s.
- The seam (WORK_ORDER.md): settings storage and PIN verification belong to React Native. The duress rule is untouched: the PIN entry screen is not changed by this task.

### Grounding in the existing code

- `app/src/settings/recipients.ts`: `normalizePhone`, `createRecipient` and the immutable editing style. The form keeps its own rows (raw phone text, so typing isn't rewritten on each keystroke) and builds `Recipient`s with `normalizePhone` at save time.
- `app/src/settings/validateSettings.ts`: returns every issue with its path (`recipients[1].phoneE164`). The form maps those paths back to its rows and shows plain-English messages next to the right field.
- `app/src/settings/SettingsProvider.tsx`: the provider-plus-hook pattern (`storage` prop for tests, a lazily made app default) to copy for the PIN store.
- `app/src/settings/defaults.ts`: limits (intervals, loudness range, name and self-description lengths) reused by the form.
- `app/src/screens/SetupScreen.tsx`: today a summary plus Start session; it gains the form.
- `app/src/screens/PinEntryScreen.tsx` and `app/src/pin/placeholderPinCheck.ts`: the PIN screen keeps the placeholder check (1111 / 9999) until K6 wires the store into it. `MAX_PIN_LENGTH` (8) becomes a shared constant.
- `app/test-utils/renderApp.tsx`, `nativeMock.ts`, `fakeFiles.ts`: full-route component tests against the native mock and the in-memory file system.

### Phases

1. Tests first (RED): PIN rules (length, digits only, must differ), the in-memory PIN store (rejects equal PINs, verify returns safe / duress / wrong), the pure form model (draft from settings, building settings, mapping validation issues to fields, row editing), and Setup screen component tests (fresh install shows the form, scenario 7 in one pass, PINs must differ, field errors, reorder, edit, cancel, PINs kept when left blank, no editing during a session).
2. Code (GREEN): `src/pin/pinRules.ts`, `src/pin/pinStore.ts`, `src/pin/PinStoreProvider.tsx`, `src/setup/setupDraft.ts` (pure), `src/setup/SetupForm.tsx` and its parts, small UI pieces in `src/ui/`, and the reworked `SetupScreen.tsx`. Debug's Reset settings also forgets the PINs.
3. Verify: jest, tsc, expo lint, swift test, and the simulator build (no new native packages expected, so no prebuild).
4. Docs, commit and push.

### Risks

- **A mistyped PIN locks the wearer out of a safe cancel, or makes them send a duress cancel by accident.** Mitigation: a "Show PINs" switch to check them before saving, digits only, 4 to 8 digits, and the "must differ" rule enforced both in the form and again inside the store.
- **The 60 s target.** Every extra tap counts. Mitigation: one scrolling screen (no wizard pages), three recipient rows ready to fill, permission defaults that already match scenario 7 (Contact 1 sees location and the full brief, Contact 2 doesn't, venue staff sees location), number pads for phones and PINs, and no confirm-PIN fields.
- **Saving settings mid-session reschedules the next check-in** (K4 decision 5). Mitigation: Edit setup is disabled while a session runs.
- **Form rows and validation paths drift apart** once empty rows are dropped. Mitigation: the builder keeps an index map from saved recipients back to form rows, with tests for a blank row in the middle.
- **PINs in memory only until K6.** They are lost when the app is killed, and the PIN screen still uses 1111 / 9999. Mitigation: the Setup summary says whether PINs are set, and this document says plainly what K6 must swap.
- **Test-state leaks through the app's shared in-memory PIN store.** Mitigation: tests clear it in `beforeEach` through an exported accessor.

## Decisions taken on Kean's behalf

1. **One scrolling form, not a multi-page wizard.** The fewest taps for the 60 s target, and every field can be checked and fixed in one place.
2. **Fresh install opens the form; Start session appears once setup is saved.** Before K5 a fresh install could start straight away on the demo defaults; that is still possible from Debug → Start session (demo).
3. **Starter permissions are chosen so scenario 7 needs no toggles:** Contact 1 gets everything (alerts, location, full brief, resolve); Contact 2 gets K4's defaults (alerts and resolve, no location, reduced brief); venue staff get alerts, location and resolve, with a reduced brief (PRD WEB-4 shows them location). Permissions travel with a recipient when it is moved.
4. **At least one contact is required; venue staff and Contact 2 are optional.** A row left completely empty is skipped, so a demo with fewer phones still saves. A half-filled row is an error.
5. **PINs: 4 to 8 digits, digits only, no confirm field, with a Show PINs switch instead.** A confirm field doubles the PIN typing; Show PINs lets the wearer check both before saving. 8 is the PIN screen's existing limit.
6. **"Must differ" is enforced twice:** in the form (the error sits on the duress PIN) and inside every `PinStore.setPins`, so K6's store has to refuse equal PINs too.
7. **Editing: leave both PINs blank to keep them; changing one means entering both.** PINs are never read back out of the store, so the fields always open blank.
8. **The PinStore interface includes `verify()`**, so K6 implements one interface for both setup and the PIN gate. The PIN entry screen was **not** changed: it still uses the placeholder 1111 / 9999 until K6 wires `verify()` in (the duress path is K6/K9's to touch).
9. **No editing during a session.** Saving calls `configure()`, which reschedules the next check-in mid-session (K4 decision 5). The summary says "Stop the session to change your setup."
10. **A failed save keeps the form open.** If `configure()` rejects after the file was written, the error is shown, the PINs are not stored, and the wearer can save again.
11. **Debug's Reset settings also clears the PINs**, so the fresh-install flow can be tried again without reinstalling. "Save sample settings" stays on Debug as a quick way to a filled-in setup.
12. **The demo flag, teammate phone and bridge URL are not on the form.** They are kept as saved; the demo toggle is K11's.
13. **Inputs use maxLength** (names 60, self-description 200, loudness 3 digits) so the length errors rarely appear; validation still checks them.
