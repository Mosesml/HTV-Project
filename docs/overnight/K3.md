# K3: navigation shell (overnight run)

Branch `kean/k3-nav-shell`, cut from `origin/main` at `b43eeb1`. Built unattended: every question was answered with the recommended option, and each answer is listed under "Decisions taken on Kean's behalf".

## Plan

### Requirements, restated

- K3 (PRD D3): a navigation shell with all six screens skeletal: Setup, Active session, Check-in, PIN entry, Alert, Debug. Depends on K2. Done when every screen is reachable on the phone.
- Expo Router, routes in `app/src/app/`. Non-route code (screens, hooks, helpers) stays outside `src/app/` (app/AGENTS.md).
- Replace the K2 smoke screen at `src/app/index.tsx`, keeping its buttons (start session, fire scenario 2, tap Cancel, stop session) and its `onPhase` / `onMotion` readout on the Debug route, so K11 grows from it.
- Set up React Native Testing Library at a version that works with React 19.2.3, RN 0.86 and jest-expo 57, with one component test per screen.
- Route by session phase from the native module (`getSnapshot` on mount, then `onPhase`): `checkIn` to Check-in, `escalated` and `sos` to Alert.
- Respect the duress rule (WORK_ORDER.md): the PIN screen shows the same "Cancelled. Stay safe." for safe and duress, and calls `pinResult` without awaiting it. After a duress PIN, Swift keeps emitting `monitoring`, so nothing in the shell may react to it differently from a safe PIN.

### Grounding in the existing code

- `app/modules/raveguard-native/index.ts`: the checked JS wrappers screens import (`configure`, `startSession`, `stopSession`, `tapCancel`, `pinResult`, `debugFire`, `getSnapshot`, `addListener`).
- `app/modules/raveguard-native/src/mock.ts`: the Jest stand-in (records calls, `emit` pushes events); already used by `app/__tests__/raveguard-native.test.ts` through `jest.mock`.
- `app/src/app/index.tsx`: the K2 smoke screen, the pattern for snapshot-then-listen (`setPhase(current => current ?? snapshot.phase)`) and the 60 pt button.
- `ios/Session/SessionManager.swift`: `tapCancel` and nods are ignored at the `pinGate` stage, so the PIN gate needs its own screen; `pinResult` also works while escalated (a late cancel), so the Alert screen links to PIN entry; `stop()` refuses unless monitoring.

### Phases

1. Tooling: add `@testing-library/react-native` and `react-test-renderer` as dev dependencies, a `jest.setup.ts` that swaps the native module for the mock in every test, and `setSnapshot` on the mock so tests can fake a relaunch mid-check-in.
2. Tests first: a pure `phaseNavigation` unit test (phase transitions to navigation actions), then one router-level component test per screen using `expo-router/testing-library`'s `renderRouter` over the real `src/app` tree.
3. Code: `SessionStateProvider` (one `getSnapshot` plus `onPhase` / `onEscalation` subscription for the whole app), `PhaseNavigator` (applies `phaseNavigation` in the root layout), six screens in `src/screens/`, thin route files in `src/app/`.
4. Verify: jest, tsc, expo lint, swift test, iOS simulator build.
5. Docs and push.

### Risks

- RNTL 14 (latest) needs the separate `test-renderer` package and an async render API, and 14.1.0 is nine days old. Mitigation: pin 13.3.3, which uses the `react-test-renderer` 19.2.3 jest-expo already ships and which expo-router 57's own tests use.
- Navigating from the root layout before the Stack mounts throws in Expo Router. Mitigation: navigation runs in an effect after the snapshot resolves, and is skipped until the root navigation state has a key.
- Phase routing that reacts to state instead of transitions would bounce the wearer back to Alert when they open PIN entry from it. Mitigation: route only when the phase or stage changes.
- Leaving the PIN screen on `monitoring` would cut the "Cancelled. Stay safe." screen short. Mitigation: the return to monitoring only auto-navigates away from Check-in; the PIN screen leaves when the wearer taps Done, the same way for both PINs.
- Typed routes: `.expo/types/router.d.ts` is generated by `expo start` and git-ignored, so a stale local copy can fail `tsc` on new routes. Mitigation: regenerate it locally if needed; it is never committed.

### How the phase moves the wearer

| Phase change | Showing | Result |
| --- | --- | --- |
| `monitoring` to `checkIn` (whisper or loud) | Anything | Push Check-in |
| `checkIn` to the `pinGate` stage | Check-in | Replace with PIN entry |
| Anything to `escalated` or `sos` | A phase screen | Replace with Alert |
| Anything to `escalated` or `sos` | Any other screen | Push Alert |
| `checkIn` to `monitoring` (nod or tap) | Check-in | Dismiss back to Active session |
| To `monitoring` (safe or duress PIN, or a resolve) | PIN entry or Alert | Stay; the wearer taps Done or Back to session |
| First snapshot is `monitoring` | Setup | Push Active session |
| Same phase and stage again (a wrong PIN, a repeat event) | Anything | Nothing |

## Decisions taken on Kean's behalf

1. **React Native Testing Library 13.3.3, not 14.1.0.** 14 needs a separate `test-renderer` package and an async `render`, and 14.1.0 came out on Oct 8 (under two weeks old). 13.3.3 runs on the `react-test-renderer` 19.2.3 that jest-expo 57 already uses, and it is the version expo-router 57's own `testing-library` is built against. Both `@testing-library/react-native` and `react-test-renderer` (pinned to 19.2.3 to match React) are in devDependencies.
2. **Tests drive the real route tree.** Screen tests use `renderRouter('./src/app')` from `expo-router/testing-library`, so the root layout, the provider and phase routing are under test too, not stubs.
3. **Screens in `src/screens/`, routes as one-line re-exports.** This follows app/AGENTS.md (no non-route code in `src/app/`) and the work order's `src/screens/` layout.
4. **Routing on change, not on state.** Without it, opening PIN entry from Alert would bounce back to Alert.
5. **The return to `monitoring` never moves the wearer off PIN entry.** Safe and duress therefore leave the same screen up until Done, which is what the duress rule needs and what K9 builds on.
6. **The PIN gate stage opens PIN entry automatically**, because Swift ignores nods and taps at that stage.
7. **Alert links to PIN entry while escalated or SOS.** `SessionManager.pinResult` accepts a late PIN while escalated.
8. **A placeholder PIN check (1111 safe, 9999 duress)** from the PRD's `FakePINVerifier` (D2), so the PIN screen and the duress test are real now. K6 replaces only `checkPlaceholderPin`. The 600 ms "Cancelling…" and the haptic are left to K9.
9. **`pinResult` failures are not shown.** Showing one could tell a safe PIN from a duress PIN. The catch is commented, and Swift logs its own failures.
10. **Call is visible but disabled** with "Calling arrives with K10", so the layout is in place without dialling anything.
11. **Placeholder settings** (demo timings, no recipients, no teammate number) go through `configure()` until K4 and K5.
12. **The escalation shown on Alert is cleared when a new check-in starts**, so a new alert never shows the last one's recipients.
13. **One global native mock in `jest.setup.ts`.** The existing `raveguard-native.test.ts` keeps its own `jest.mock`, which is harmless and left alone.
14. **No prebuild.** No native package was added and `app.json` is unchanged, so the simulator build ran on the existing `ios/` after `pod install`.

## Contract changes

None to the native module API: no change to `src/RaveGuardNative.types.ts`, `index.ts`, `src/RaveGuardNativeModule.ts`, `ios/RaveGuardModule.swift` or `ios/Module/RaveGuardRuntime.swift`.

One test-only addition to the Jest stand-in, `modules/raveguard-native/src/mock.ts`:
- `setSnapshot(snapshot)` sets what `getSnapshot()` resolves to (for example, a relaunch mid-check-in), and `reset()` puts it back to idle. Existing behaviour is unchanged.

`package-lock.json` note: with RNTL installed, npm counts it as satisfying expo-router's optional peer dependency, so jest's packages lose their `"dev": true` lockfile flag. That only matters for `npm install --omit=dev`, which we never run.

## How to test it

Simulator: `cd app && npx expo run:ios`. Phone: `cd app && npm run ios:device`. Both need `app/.env.local` (see app/README.md). The module runs on its fakes, with demo timings (whisper 10 s, loud 10 s, PIN gate 15 s).

| Step | Do this | Expect |
| --- | --- | --- |
| 1 | Launch the app | Setup: "Set up RaveGuard", with Start session and Debug buttons |
| 2 | Tap Debug | Debug: `onPhase` reads `idle`; the four K2 buttons are there. Go back |
| 3 | Tap Start session | Active session: "Session running", Status: Monitoring |
| 4 | Tap Debug, then Fire scenario 2 (fall) | Check-in opens on its own: dark full screen, "Are you okay?", "Nod if you're okay.", a seconds countdown, a large Cancel |
| 5 | Tap Cancel | Back on Active session (Debug was closed too) |
| 6 | Debug, Fire scenario 2, then wait about 20 s | The hint changes to "Nod, or tap Cancel.", then PIN entry opens on its own: "Enter your PIN" |
| 7 | Enter 1111 and tap Submit | "Cancelled. Stay safe." Tap Done to return to Active session |
| 8 | Repeat step 6, then enter 9999 | Exactly the same "Cancelled. Stay safe." screen as step 7 |
| 9 | Repeat step 6, then enter 1234 three times | "Wrong PIN. Try again." after each of the first two; the third opens Alert: "Alert sent", a status line, a disabled Call button, Enter PIN to cancel |
| 10 | On Alert, tap Enter PIN to cancel and enter 1111 | "Cancelled. Stay safe."; Done returns to Active session |
| 11 | Repeat step 6 and let the PIN gate run out (15 s) | Alert opens on its own. Left alone, the heading changes to "SOS" when the fake ladder reaches it |
| 12 | During a check-in, go to Debug and tap Stop session | "Stop refused: answer the check-in or escalation first." |
| 13 | While monitoring, tap Stop session on Active session | Back on Setup |
