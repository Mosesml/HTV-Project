## Plan

### Requirements, restated

- K10 (PRD D10, UI-5): the Alert screen, opened from `onEscalation` / the `escalated` and `sos` phases, shows **what was sent and to whom** (each recipient's `notifiedAt`), **who acknowledged** (`ackedAt`), the escalation `state`, and the **SOS state** (phase `sos` or `sosOpen`). Depends on K3.
- A **Call** button dials `teammatePhone` from the saved settings, **only in demo mode**, through `Linking` and a `tel:` URL. Outside demo mode, or with no teammate number, it dials nothing. No code path may ever dial an emergency number (PRD DEM-1), and a test asserts that no emergency number appears in the app code.
- Done when: an ack on Contact 1's page shows here within 5 s. The real check needs Andy's server, so it is verified here against the mock (JavaScript) and the scripted escalation service (Swift), and the real-server check is listed as manual.
- The duress rule still holds: Swift never sends an `onEscalation` for a duress PIN, so this screen never shows one; nothing here may change that.

### Grounding in the existing code

- `app/src/screens/AlertScreen.tsx` (K3 skeleton): title, `Status: <state>`, one `describeRecipient` line per recipient, a disabled Call, Enter PIN to cancel while open, Back to session once closed. K10 replaces the body and keeps both navigation buttons.
- `app/src/session/SessionStateProvider.tsx`: `useSessionState()` already gives `phase` and `escalation` (snapshot first, then every `onEscalation`), so live acks need no new subscription.
- `app/src/settings/SettingsProvider.tsx` (K4): `useSettings()` gives `settings.demo` and `settings.teammatePhone`; `save()` validates (`E164_PATTERN` in `validateSettings.ts`), writes and calls `configure()`.
- No screen sets `teammatePhone` yet (K5 decision 12 left it off the Setup form). The Debug screen (`app/src/screens/DebugScreen.tsx`) already holds the demo-only tools, so the number goes there.
- `app/modules/raveguard-native/ios/Session/SessionManagerConfig.swift`: `statusPoll: 3` s in both timings, and `sosDialNumber` is the teammate in demo, nil otherwise. The JS side mirrors that rule.
- `app/modules/raveguard-native/ios/Tests/.../SessionWiringTests.swift`: the Swift emergency-number scan (`(?<![0-9_.])(911|112|999|000)(?![0-9_.])`); the JS test uses the same numbers.
- `app/__tests__/screens/AlertScreen.test.tsx`, `test-utils/renderApp.tsx` (`emitEscalation`, `emitPhase`): the screen-test pattern through the real route tree.
- `app/src/ui/ActionButton.tsx` (`size="large"`, `accessibilityHint`), `theme.ts`, `ReadingTile.tsx`: the shared UI.

### Risks

- **Dialing the wrong number.** Mitigation: the only `tel:` URL in the app is built in one function from the saved `teammatePhone`, only when `demo` is on and the number matches E.164 with 8 to 15 digits (no short code can pass); a test scans the app code for emergency numbers and for any other `tel:`.
- **The Simulator has no phone.** `Linking.openURL('tel:…')` rejects there. Mitigation: the rejection is caught and the screen says the call couldn't start and shows the number to dial by hand.
- **Ack latency.** The 5 s budget depends on Swift polling the server (3 s) and the screen re-rendering. Mitigation: the Swift test measures poll-to-event on the scripted server; the JS test shows the ack renders on the event with no timer in between.
- **Time formatting in tests** depends on the machine's time zone. Mitigation: times are formatted from local `Date` parts and tests build expected strings the same way.
- **Saving the teammate number calls `configure()`**, which reschedules the next check-in during a running session (K4). Mitigation: documented; it is a pre-demo setting on the Debug screen.

A mutation check was run by hand afterwards: letting `callTarget` ignore the demo flag and planting `'tel:' + '911'` in `src/` made 4 tests fail (then both were reverted).

## Decisions taken on Kean's behalf

1. **"Demo mode" is the saved `settings.demo`.** That is what Setup keeps and what `configure()` sends. (Debug's "Start session (demo)" forces demo timings in Swift whatever is saved; with the default settings both are on, so it only matters once K11's demo toggle can turn it off.)
2. **Outside demo mode Call is shown but off**, with "Calling is only on in demo mode. RaveGuard never dials emergency services." Hiding it would leave the wearer wondering where it went; dialling anything else is out (DEM-1).
3. **The teammate's number lives on the Debug screen**, not the Setup form (K5 decision 12 kept demo settings off the form; K11 adds the demo toggle there too). Sample settings fill in a fictional `+14165550199` so the button can be tried at once; put a real teammate's number in before the demo.
4. **A `tel:` URL needs a full E.164 number** (the same pattern as settings validation: `+`, then 8 to 15 digits). Every emergency short code is 2 to 4 digits, so none can ever pass, without the code having to list emergency numbers to block them (which would itself trip the scan).
5. **Call is never automatic**, not even at SOS: the wearer taps it, and iOS's own "Call …?" confirmation follows. The brief asks for a simulated emergency call, and a phone dialling on its own in a pocket is worse than one more tap.
6. **React Native's `Linking.openURL`**, no `canOpenURL` first (that needs `LSApplicationQueriesSchemes` in `app.json`, so a rebuild). A phone that can't call (the Simulator, an iPad) rejects, and the screen shows the number to dial by hand.
7. **SOS is phase `sos` or `sosOpen`**, unless the alert has been acknowledged, resolved or cancelled: an ack stops the chain (the server clears `sosOpen`), so a stale flag must not keep the screen red.
8. **Times are local 24-hour HH:MM**, like the SMS briefs ("Checked in at HH:MM", B14).
9. **The screen stays light with the stack header**, like Session and PIN entry; only the SOS banner goes full red. Check-in is the one dark screen because it is read in a dark room at arm's length; the Alert screen is read after the wearer has already engaged.
10. **The K3 test "Call is shown but disabled until K10" was replaced** by the Call tests above, and the K3 "Sam: texted" lines by the new rows.
11. **No live "updated N s ago" readout.** It would need the provider to stamp `onEscalation` arrivals; the 5 s budget is covered by the Swift poll test and the manual check below.

## Contract changes

None to the native module API: no changes to `src/RaveGuardNative.types.ts`, `index.ts`, `src/mock.ts`, `ios/RaveGuardModule.swift` or `ios/Module/RaveGuardRuntime.swift`. `onEscalation`, `getSnapshot().escalation` and `Settings.demo` / `teammatePhone` are used exactly as the seam table describes.
