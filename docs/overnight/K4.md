# K4: settings storage (overnight run)

Branch `kean/k4-settings`, cut from `kean/k3-nav-shell` at `097a317`. Built unattended: every question was answered with the recommended option, and each answer is listed under "Decisions taken on Kean's behalf".

## Plan

### Requirements, restated

- K4 (PRD D4, UI-1, PRV-3): store the wearer's settings on the phone: recipients and their order, four permissions per recipient (alerts, location, full brief, resolve), check-in interval, loudness target, self-description and bridge URL, plus the other fields of the module's `Settings` (wearer name, demo flag, teammate phone). Depends on K2. Done when settings survive a relaunch.
- Send them to Swift through `RaveGuard.configure()` using the exact `Settings` type in `app/modules/raveguard-native/src/RaveGuardNative.types.ts`.
- Use an Expo-supported persistent store suitable for SDK 57. PINs are not stored here (K6, `expo-secure-store`).
- Validate in TypeScript with clear errors, and generate recipient UUIDs.
- Unit-test the store and the validation against the module mock.
- The seam (WORK_ORDER.md): settings storage is React Native's job; Swift keeps only what `configure()` hands it, in memory. The duress rule is untouched by this task.

### Grounding in the existing code

- `app/modules/raveguard-native/src/RaveGuardNative.types.ts`: `Settings`, `Recipient`, `RecipientPermissions`, `RecipientKind`.
- `app/modules/raveguard-native/ios/Module/ModuleSettings.swift` and `ModuleFields.swift`: what Swift rejects. Interval 30 or 60; loudness 0–120 dB; non-blank wearer and recipient names; recipient `id` must parse as a UUID; E.164 regex `^\+[1-9][0-9]{7,14}$`; `bridgeUrl` must be http or https with a host. The TypeScript validator mirrors these so a saved file never fails in Swift.
- `app/modules/raveguard-native/ios/Shared/Contracts.swift`: `PermissionSet` defaults (alerts on, location off, full brief off, resolve on), reused as the default for new recipients.
- `app/modules/raveguard-native/ios/Session/SessionManager.swift`: `configure()` while monitoring reschedules the next check-in, so the app must not re-send settings on every launch.
- `app/src/session/placeholderSettings.ts`: what Setup and Debug send today; it becomes the defaults.
- `app/src/session/SessionStateProvider.tsx`: the provider-plus-hook pattern to copy for settings.
- `app/jest.setup.ts`, `app/test-utils/`: the global native mock and `renderApp()`.

### Phases

1. Dependencies: `npx expo install expo-file-system expo-crypto` (both SDK 57 versions).
2. Tests first (RED): `validateSettings`, recipient editing (add, update, remove, move, permissions, order renumbering, UUIDs), the store (load defaults when empty, round trip, corrupt or invalid file, save rejects invalid settings, save calls `configure()` with exactly what was saved, temp-file recovery), the file storage adapter against a fake `expo-file-system`, the provider, and the Setup and Debug screens.
3. Code (GREEN): `app/src/settings/` with defaults, validation, recipient helpers, the file storage, the store and `SettingsProvider`; wire Setup and Debug to it; remove `placeholderSettings.ts`.
4. Verify: jest, tsc, expo lint, swift test, prebuild, pod install and the simulator build (both packages are native).
5. Docs, commit and push.

### Risks

- A file written halfway (app killed mid-save) would lose the recipients. Mitigation: write `settings.json.tmp`, then move it over `settings.json`; on load, fall back to the temp file if the main file is missing.
- A corrupt or old-format file at launch would crash or silently wipe settings. Mitigation: load never throws; it returns the defaults plus a readable problem, and the bad file stays until the next save.
- TypeScript and Swift validation drift apart, so a saved file is refused by `configure()`. Mitigation: the same rules and limits, and tests that use Swift's own edge cases (blank names, bad UUIDs, `+0` phones, non-http URLs).
- Re-sending settings at launch while Swift still runs a session would push the next check-in later. Mitigation: send through `configure()` on save and right before Start session, not on launch.
- New native packages: every teammate's dev build has to be rebuilt. Mitigation: `expo-file-system` was already compiled in (a dependency of `expo`); only `expo-crypto` is new, and K6 needs it anyway for salts and hashes.
- Jest has no native file system or crypto. Mitigation: `jest.setup.ts` installs an in-memory `expo-file-system` fake and an `expo-crypto` stand-in backed by Node's `crypto.randomUUID`.

## Decisions taken on Kean's behalf

1. **A JSON file through `expo-file-system`, not AsyncStorage or SQLite.** Expo's "Store data" guide names no single default for this. A file matches PRD D4 ("Codable, saved to a file"), and `expo-file-system` was already compiled into everyone's dev build as a dependency of `expo`, so it adds no native code. It is now listed in `package.json` because the app imports it directly. Settings are not secrets (phone numbers and names), so they don't belong in `expo-secure-store`, which is meant for small values such as PINs and keys.
2. **`expo-crypto` for recipient UUIDs.** Hermes' support for `crypto.randomUUID` isn't something to rely on, and K6 needs `expo-crypto` anyway for salts and hashes. This is the one new native package, so **every teammate needs one rebuild (`npm run ios:device`)** after pulling this.
3. **Hand-written validation, not zod.** The validator mirrors Swift's `ModuleSettings` field by field, with the same messages and paths. A schema library would add a dependency without cutting much code.
4. **Stricter than Swift in four places:** all four permissions must be present (Swift fills in defaults); names are capped at 60 characters and the self-description at 200 (the SMS must fit in 300); `order` must equal the position in the list; no two recipients may share an id or a phone number.
5. **Settings go through `configure()` on save and right before Start session, not at launch.** `SessionManager.configure` reschedules the next check-in while monitoring, so resending on every JavaScript reload would push check-ins back mid-session.
6. **Loading never throws and never deletes.** A damaged or unknown-version file gives the defaults and a visible problem line on Setup, and stays on disk until the next save.
7. **New recipients get Swift's `PermissionSet` defaults** (alerts and resolve on, location and full brief off) whatever their kind, so new recipients share as little as possible. The setup flow (K5) can offer venue staff location by default if Kean wants that.
8. **`normalizePhone` assumes North America** for 10-digit numbers and 11-digit numbers that start with 1 (the team's phones are Canadian). Anything else has to be typed in E.164.
9. **Defaults stay the K3 placeholder values** (wearer "Demo wearer", 30 min, 85 dB, demo on, nobody to text) with an empty self-description, so a fresh install can still start a demo session.
10. **Test path on the phone through Debug buttons**, not a settings form: the editing UI is K5's job. Save sample settings and Reset settings exist so K4's done-when can be checked today.
11. **Debug's Start session (demo) uses the saved settings with `demo: true`** rather than separate placeholder settings, so there is only one source of settings.
