## Plan

### Requirements, restated

- K8 (PRD D9, UI-2, HRG-5): the Active session screen shows room dB, dose, protection level, motion state, the next check-in and a large Stop. Depends on K3.
- Room dB and dose come from `onHearing` and are null until backlog BL1 lands, so each shows "—" while null. Dose is labelled an estimate (HRG-2).
- Protection level comes from `onNoise`; motion state from `onMotion` (10 Hz).
- A manual slider, 0 to 100, calls `RaveGuard.setProtectionLevel(level)` and shows what `onNoise` reports back (HRG-5, the fallback that must work whatever happens to the Shortcuts backend).
- Next check-in "if available": the module does not send it today.
- Large Stop calls `stopSession()`; when that resolves `false` (a check-in or alert is open) the screen stays and says why in plain words.
- Component tests with the module mock.
- Done when: the slider changes Moses's fake noise output (`FakeNoiseController` and the `onNoise` it causes).

### Risks

- **A new native package.** The slider needs a rebuild on every phone. The snapshot field is a Swift change that needs one anyway, so it's one rebuild, and `@react-native-community/slider` is the slider Expo lists for SDK 57.
- **Flooding Swift while dragging.** `onValueChange` fires on every step of a drag, and each call makes Swift emit `onNoise`. Mitigation: a latest-wins sender keeps one call in flight and sends only the newest level after it, so a fast drag sends a handful of calls and always ends on the final value.
- **VoiceOver never fires "sliding complete".** UISlider's swipe up and down only send value changes, so the slider sends on value change (through the sender), not only on release.
- **Thumb jitter.** If the slider's `value` followed the lagging `onNoise` level during a drag, the thumb would jump back. Mitigation: the slider shows the wearer's chosen level until `onNoise` confirms it (or the call fails); the number on screen is what `onNoise` reports.
- **Next check-in.** `onPhase` fires before Swift schedules the next check-in, so it can't ride on the event without editing Justin's `SessionManager`. Mitigation: read it from `getSnapshot()` whenever the phase becomes `monitoring`; the Swift call runs after the scheduling, so it's always current. Null in demo mode, shown as "—" with a hint.
- **Slider in Jest.** The native slider is a host component under Jest; tests drive its `onValueChange` and `onSlidingComplete` props.

## Decisions taken on Kean's behalf

1. **`@react-native-community/slider`**, installed with `npx expo install` (5.2.0 for SDK 57). It's the slider Expo documents, VoiceOver gets a real adjustable control, and a rebuild was due anyway for the Swift snapshot change. Rejected: a hand-made slider from plain Views (more gesture code and weaker VoiceOver for no gain once a rebuild is needed), and `@expo/ui`'s SwiftUI slider (harder to test under Jest).
2. **Send on value change, latest wins.** VoiceOver's swipe up and down never fire "sliding complete", so sending only on release would leave VoiceOver users without the slider. A drag fires every step, so `levelSender` keeps one call in flight and only sends the newest level after it. Release also calls the same handler; it sends nothing if the drag already did.
3. **The number is Swift's, the thumb is the wearer's.** The big level and the mode line show what `onNoise` reports (the "reflects onNoise" rule). The thumb stays where the wearer put it until `onNoise` confirms that level, or the call fails and it goes back.
4. **Next check-in through the snapshot (an approved contract change).** `onPhase` fires before Swift schedules the next check-in, and its payload is built in Justin's `SessionManager.swift`, so putting it on the event would mean editing Justin's file and reordering his state machine. `RaveGuardRuntime.snapshot()` reads `SessionManager.nextCheckIn` at call time instead, and the screen re-reads the snapshot on every phase change. Demo mode has no scheduled check-ins, so it shows "—".
5. **"—" for every unknown value**: room dB, dose, motion before the first readout, next check-in, and the level before the snapshot.
6. **Dose is labelled "Sound dose (estimate)"** (PRD HRG-2) and can go past 100%.
7. **The mock now answers like Swift**: `setProtectionLevel` and `setNoiseBackend` update the snapshot's noise and emit `onNoise`, matching `RaveGuardRuntime` (including "every backend but off connects"). No existing test depended on the old silence.
8. **VoiceOver reads "55 points", not "55%"**: the work order says the level is a policy score, not a share of sound blocked, and the slider's default would read a percentage.
9. **Stop is the large (120 pt) red button** from K7, with a hint that it can't stop during a check-in or alert. The refused message names what to do: "answer the check-in or alert first, then stop."
10. **Readings stay out of SessionStateProvider.** Its rule is to keep 10 Hz motion out of the app-wide context; the screen has its own hook, which only re-renders when the motion state changes.
11. **Light theme kept.** The screen uses the app's standard light layout like Setup; a dark session theme is part of the later polish pass (D12), not K8.
12. **No backend picker here.** `setNoiseBackend` stays on the Debug panel (K11); the screen only shows which backend is in use.
