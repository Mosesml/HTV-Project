# K11: Debug panel (overnight run)

## Plan

### Requirements, restated

- K11 (PRD D11, UI-6, DEM-2): grow the Debug screen into the Debug panel. It needs:
  - **7 scenario buttons**, one per PRD acceptance scenario (1 Safe, 2 No response, 3 Duress, 4 Connectivity failure, 5 Unacknowledged, 6 False alarm, 7 Privacy), each calling `debugFire(n)`.
  - A **live motion readout** from `onMotion` (10 Hz).
  - A **demo/real timing toggle**, saved through K4's `useSettings().save` (validate, write, `configure()`).
  - A **noise backend picker** calling `setNoiseBackend`.
  - A **"simulate offline" switch** calling `debugSetOffline`, the backup for real airplane mode (PRD D11, DEM-2).
  - **Start session and Stop session.**
- Component tests for each control. Depends on K3.
- Done when: each of the 7 buttons fires its scenario.
- Nothing here may weaken the duress rule: the panel only sends taps down, and it never reads or shows which PIN was entered.

### Risks

- **The offline switch lying.** Scenario 4 turns simulated offline on inside Swift, and `stop()` turns it off, so a switch that only remembered its own taps would show the wrong state, and a demo could stay "offline" by accident. Mitigation: a contract change adds `simulatedOffline` to the snapshot, and the switch re-reads it on mount, after each phase change, after each toggle and every second while the panel is mounted.
- **A scenario fired while a check-in is open does nothing** (Swift ignores the trigger). Mitigation: the buttons are disabled then, with the reason on screen.
- **Firing from idle without settings.** Swift's `debugFire` starts the session with whatever it was last configured with. Mitigation: from idle, the panel sends the saved settings through `configure()` first, like Start session does.
- **10 Hz motion re-rendering the whole panel.** Mitigation: `MotionReadout` subscribes to `onMotion` itself, so only it re-renders.
- **The demo toggle during a running session** calls `configure()`, which reschedules the next check-in (K4). That is the intended effect (real timings take over), and it is documented.

TDD note: the scenario model, the five component suites, the rewritten Debug screen suite and the Swift snapshot tests were written before their code and failed first (the new modules didn't exist, so the JS suites failed on import; the Swift snapshot tests failed on the missing key). The JS wrapper test for `simulatedOffline` was added in the same step as the mock change, so it was never seen failing on its own. The Swift test that fires each of the 7 scenarios from idle passed straight away: Justin's `SessionManager.debugFire` already handled all seven, so it confirms the done-when rather than driving new code. A mutation check was run by hand afterwards: making every button fire scenario 1 and making the offline switch always send `false` failed 9 Debug screen tests (both reverted).

## Decisions taken on Kean's behalf

1. **Button labels** are "Scenario N: <PRD name>" (Safe, No response, Duress, Connectivity failure, Unacknowledged, False alarm, Privacy), with the trigger ("Fall." or "Manual trigger.", mirroring Swift) and the next step written under each button and used as its VoiceOver hint.
2. **From idle, a scenario button sends the saved settings through `configure()` first**, then `debugFire(n)`. Swift starts the session itself on `debugFire` from idle and would otherwise use whatever it was last configured with. While monitoring it sends only `debugFire` (configure would reschedule the next check-in).
3. **The scenario buttons are disabled while a check-in or alert is open**, with "A check-in or alert is open. Answer it before firing another scenario." Swift ignores a trigger then, so an enabled button would do nothing silently.
4. **Start session now uses the saved demo flag** instead of forcing `demo: true` (the K2/K3 behaviour). Its label says which: "Start session (demo timings)" or "Start session (real timings)". Defaults are demo, so nothing changes for a fresh install.
5. **The demo toggle saves straight away** through `useSettings().save({ ...settings, demo })` (validate, write, `configure()`), and says "Demo timings saved" or "Real timings saved". A failed save shows the reason and the switch stays on the saved value. During a running session this reschedules the next check-in, which is what switching to real timings should do.
6. **The noise picker offers Shortcuts and Off only.** The Linux bridge is cut in WORK_ORDER.md and the PRD; the module still accepts `'bridge'`, but the panel doesn't offer it. The picker shows what `onNoise` reports, not what was tapped.
7. **"Simulate offline" shows Swift's state, not its own taps**, through a new snapshot field (decision 8). Scenario 4 turns it on inside Swift and `stopSession()` turns it off, so a switch that only remembered its own taps would be wrong after either. It re-reads on each phase change rather than polling, which keeps screen tests free of stray timers. Scenario 4 flips it while the Check-in screen is up, and the next phase change re-reads it.
8. **Contract change: `Snapshot.simulatedOffline: boolean`** (approved by the team for this run). It was preferred over a new event because it changes rarely and the snapshot already carries the other state JS can't see (`nextCheckInAt`).
9. **The motion readout is its own component with its own `onMotion` subscription**, so the 10 Hz feed doesn't re-render the whole panel (the same reason SessionStateProvider leaves motion out). It adds a readout count so a stalled feed is visible. The old one-line text is kept as its VoiceOver label.
10. **Tap Cancel stays** on the panel (now a secondary button) next to Start and Stop, and Stop's refusal is shown as the panel's error line.
11. **Errors and notices are one line each for the whole panel** (`useDebugRunner`), as before; K10's teammate field reports through the same notice line.

## Test it in the Simulator or on the phone

The Swift file changed, so rebuild once: `cd app && npx expo run:ios` (Simulator) or `cd app && npm run ios:device` (phone). After that, `npm start` is enough for JavaScript changes.

1. Open the app, tap **Debug**. Expected: onPhase reads `idle`; the onMotion card says "no readouts yet (start a session)"; the start button reads **Start session (demo timings)**; seven scenario buttons, each with a "Fall." or "Manual trigger." line under it; Demo timings on; noise backend **Off** with "Backend: off · not connected"; Simulate offline off.
2. Tap **Start session (demo timings)**. Expected: onPhase becomes `monitoring`; the motion card shows state, pitch, roll and accel changing about 10 times a second and the readout count climbing.
3. Tap **Scenario 1: Safe**. Expected: the notice "Scenario 1 (Safe) fired. Nod, or tap Cancel…" flashes and Check-in opens at "Step 1 of 3: Whisper". Tap **Cancel**. Expected: back to the session; go back to Debug.
4. Repeat for **Scenario 2** to **Scenario 7** from Debug while monitoring. Expected for each: Check-in opens at Whisper. Then:
   - 2 and 5 and 7: ignore everything. After about 35 s the Alert screen opens. For 5 and 7, wait about 95 s for SOS. Cancel with the safe PIN from Alert (Enter PIN).
   - 3: wait for the PIN gate (about 20 s), enter the **duress PIN**. Expected: "Cancelling…" then "Cancelled. Stay safe.", identical to a safe PIN; afterwards Debug's onPhase reads `monitoring` and no Alert opens.
   - 4: Expected: after the check-in opens, go back to Debug when you can (after cancelling): **Simulate offline is on** (Swift turned it on). Tap **Stop session**. Expected: Simulate offline turns off by itself.
   - 6: let it reach the Alert screen, then cancel with the safe PIN. Expected: back to the session, no further alerts.
5. With the session idle, tap **Scenario 2** straight away (no Start). Expected: the session starts (onPhase `monitoring` briefly) and Check-in opens: the saved settings went through configure() first.
6. Open a check-in (any scenario), go back to Debug without answering it (swipe back, if the Check-in screen allows it; otherwise skip this step, it is covered by `ScenarioButtons.test.tsx` and `scenarios.test.ts`). Expected: all seven buttons greyed out with "A check-in or alert is open. Answer it before firing another scenario." Answer it, and they come back.
7. Turn **Demo timings** off. Expected: "Real timings saved", the hint line switches to real timings, and the start button reads **Start session (real timings)**. Relaunch the app. Expected: still off. Turn it back on before the demo.
8. Tap **Shortcuts** under Noise backend. Expected: it becomes selected and the line reads "Backend: shortcuts · connected" (the fake connects every backend). Tap **Off**. Expected: "Backend: off · not connected".
9. During a session, turn **Simulate offline** on. Expected: it stays on (Swift confirmed). Turn it off. Expected: it stays off. Turn it on, then **Stop session**. Expected: it turns off by itself.
10. Tap **Stop session** while a check-in is open (from step 6). Expected: "Stop refused: answer the check-in or escalation first."
